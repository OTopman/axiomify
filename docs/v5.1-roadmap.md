# v5.1 roadmap (historical)

> **Note:** Historical planning document from the 5.x cycle. The codebase
> is now at v6.0.0. See [CHANGELOG.md](../CHANGELOG.md) for what actually shipped.

This is a forward-looking design document, not a commitment. It captures
the themes the audit work surfaced as logical next investments after
5.0.0 ships and stabilises. Each theme is sized and scored on its own
merits so the maintainer can pick what to actually pursue.

Themes are listed in roughly the order I'd ship them. None of them
require breaking changes — `5.1.0` should be a strict superset of `5.0`.

---

## Theme 1 — Tooling polish (~ 1 week)

The lowest-risk, highest-leverage v5.1 work. The 5.0 CLI gained
`openapi` / `check` / `doctor` and a redesigned `routes` output;
v5.1 closes the gaps that emerged from using those daily.

### 1.1 — `axiomify scaffold route`

Scaffold a new route into an existing app:

```bash
axiomify scaffold route GET /users/:id
axiomify scaffold route POST /users --auth --rate-limit
axiomify scaffold route WS /chat
```

Generates a TypeScript file under `src/routes/`, prompts to register it
in `src/index.ts`. Avoids the boilerplate-copy-paste pattern most users
fall into on their second day.

**Acceptance criteria:**
- Generates an `app.route({ method, path, schema, handler })` block with
  empty Zod schemas pre-stubbed.
- `--auth` adds `plugins: [requireAuth]` and inserts an import.
- `--rate-limit` adds the rate-limit plugin and a sensible default
  config.
- `WS` first arg generates `app.ws({ path, schema: { message: ... }, ...})`.
- Idempotent: re-running on an existing path returns "already exists"
  instead of overwriting.

### 1.2 — `axiomify migrate` (v4 → v5 codemod)

Automated migration of v4 codebases. Walks the source AST and applies:

- `meta: { ... }` → in v6, merged into `schema:` on route definitions
- `useSwagger` → `useOpenAPI` imports
- `routePrefix: ...` → `prefix: ...` on `useOpenAPI()` options
- `RouteMeta` → `OpenApiOperation` type references
- Inserts `app.enableRequestId()` at the right point if any test or
  comment mentions `X-Request-Id` (heuristic — flagged in a report,
  not silently applied).
- Flags unused 5-arg serializer signatures with a hint to migrate by
  hand (positional → object).

**Acceptance criteria:**
- `--dry-run` mode prints a unified diff without writing.
- `--report-only` produces a markdown migration report.
- Idempotent: running twice on the same file is a no-op.
- Bundled corpus of test cases in `packages/cli/tests/migrate-corpus/`.

### 1.3 — `axiomify routes --diff <baseline>`

Compare the current route surface against a `routes.json` snapshot:

```bash
axiomify routes --json > routes-main.json
# … on a feature branch …
axiomify routes --diff routes-main.json
```

Output: routes added, removed, signature-changed (method or schema).
Exit code 1 on any breaking change (removed route, narrowed schema,
method changed). Wires into the same CI you already have for
`axiomify check`.

### 1.4 — `axiomify openapi --validate`

Validate the generated spec against the OAS 3.0.3 / 3.1 JSON Schema.
Catches `responses` missing required `description`, `parameters` with
contradictory `in:` / `required:` shapes, etc. Useful in CI as a hard
gate.

## Theme 2 — HTTP/2 and HTTP/3 (~ 2-3 weeks)

uWS supports HTTP/2 (and HTTP/3 via QUIC) but the adapter exposes only
HTTP/1.1. Mobile clients especially benefit from HTTP/2 multiplexing
(no head-of-line blocking) and connection coalescing.

### 2.1 — HTTP/2 ALPN

```ts
new NativeAdapter(app, {
  port: 443,
  tls: { keyFile: '...', certFile: '...' },
  protocols: ['h2', 'http/1.1'],   // ALPN preference order
});
```

**Acceptance criteria:**
- `h2c` (cleartext HTTP/2 for testing) supported via `protocols: ['h2c']`.
- HTTP/2 server push intentionally NOT supported (deprecated by all
  major browsers — not worth implementing).
- `Trailer` headers exposed via a new `res.setTrailer(name, value)`.

### 2.2 — HTTP/3 (QUIC)

Behind a feature flag because uWS's QUIC support is newer:

```ts
new NativeAdapter(app, {
  experimental: { http3: true },
  tls: { ... },
  port: 443,
});
```

**Risk:** uWS QUIC implementation has not been battle-tested at scale
in the wider ecosystem. We should treat this as `experimental:` until
two major versions of stable real-world usage.

## Theme 3 — OpenAPI 3.1 + JSON Schema 2020-12 (~ 1 week)

5.0 ships 3.0.3. 3.1 is current spec. Differences relevant to the
generator:

- 3.1 `nullable: true` → `type: [..., 'null']` (JSON Schema 2020-12).
- 3.1 adds `prefixItems` for tuple types — matches Zod's `z.tuple()` exactly.
- 3.1's `examples` field everywhere (replaces `example`).
- 3.1's `webhooks` at the document root (not Operation).

```ts
useOpenAPI(app, {
  oasVersion: '3.1.0',   // default 3.0.3 through 5.x
  info, prefix, ...
});
```

**Acceptance criteria:**
- Both 3.0.3 and 3.1 outputs validate against their respective schemas.
- A test corpus of representative Zod schemas exists with snapshot
  outputs for both versions.
- Swagger UI (which supports both) renders both correctly.

## Theme 4 — Streaming primitives beyond SSE (~ 2 weeks)

The current `res.stream()` / `res.sseSend()` API is tight but limited:

### 4.1 — WebTransport

Bidirectional, ordered + unordered streams over QUIC. Unlocks
low-latency real-time apps (game servers, collaborative tools, live
audio) without the WebSocket framing overhead. Depends on Theme 2.

### 4.2 — Chunked responses with trailers

```ts
res.setTrailer('X-Final-Total', totalBytes);
res.stream(readable);
// trailers emitted after the readable closes
```

Required for HTTP/2 properly. Currently the `Trailer` header from the
audit is a known limitation.

### 4.3 — `res.sse` async iterator

Replace the imperative `sseInit` / `sseSend` with a structured API:

```ts
for await (const update of orderUpdates(orderId)) {
  yield { event: 'update', data: update };
}
```

Backwards-compatible with the existing `sseInit`/`sseSend`.

## Theme 5 — Real fuzz harness (~ 1 week)

`fast-check` (already in v5) covers property-based testing of the query
parser. v5.1 should add:

### 5.1 — wycheproof JWT test vectors

The Google project ships ~2,000 JWT attack vectors covering algorithm
confusion, malformed signatures, edge-case claim shapes, and known CVE
reproducers. Run the entire corpus against `createAuthPlugin` in CI.

### 5.2 — AFL-style mutation fuzzing of the body parser

`readBody` + `parseBodyBuffer` are the highest-surface-area attack
points after the routing layer. Run libFuzzer / honggfuzz against the
parser binary with seed corpora of legitimate JSON / form bodies.

### 5.3 — Smuggling test suite

HTTP request smuggling regression tests: malformed `Content-Length` +
`Transfer-Encoding` combos, `\r` vs `\n` line-ending edge cases, header
value injection. uWS handles most of this at the protocol layer; the
test suite proves it.

## Theme 6 — Observability surface (~ 1 week)

`@axiomify/metrics` is Prometheus-only. v5.1 broadens observability
without adding heavy deps:

### 6.1 — OpenTelemetry trace propagation

Auto-extract `traceparent` / `tracestate` headers; expose
`req.state.traceContext` for hooks. Optional dep on `@opentelemetry/api`
— the adapter's hot path stays clean when the package isn't installed.

### 6.2 — Structured logging contract

`AxiomifyLogger` is currently `{ warn, error }`. Extend to
`{ trace, debug, info, warn, error, fatal }` with consistent metadata
shape. Pino / Winston / Bunyan all match this contract; users plug in
whichever they prefer.

### 6.3 — Server-Timing header emission

`Server-Timing: app;dur=2.4, db;dur=5.1, total;dur=8.2` — surfaced
automatically when handlers do `req.state.timings.start('db')`.
Browser devtools render this natively.

## Theme 7 — Plugin ecosystem hardening (~ ongoing)

### 7.1 — Plugin encapsulation

Fastify's killer feature is plugin encapsulation — child contexts that
inherit from parents but can't pollute them. Axiomify doesn't have
this. Adding it without breaking the module system requires careful
design:

```ts
app.encapsulate((scope) => {
  scope.use(somePlugin);     // visible only inside this scope
  scope.route({ ... });
});
```

Big design surface. Probably v5.2 not v5.1.

### 7.2 — Plugin metadata standardisation

Every `useX(app, options)` plugin should expose:

```ts
useX.meta = {
  name: '@axiomify/cors',
  version: '5.0.0',
  hooks: ['onRequest'],
  routes: [],
};
```

Lets `axiomify check` and `axiomify doctor` enumerate installed plugins
without name-matching on hook callbacks.

## Out of scope for v5.1

- Native ESM at the framework level. The build is dual ESM/CJS;
  consumer projects can use either. Switching the internals to ESM-only
  cuts out CJS users without a real benefit.
- Bun / Deno first-class support. uWS is the floor of the perf claim;
  changing transports is a different framework, not a version bump.
- Custom router. The two-router design (uWS native + JS trie for
  `app.handle()`) is solid. Replacing the trie with anything more
  complex makes routing slower at every entry point.
- Form fields beyond `multipart/form-data`. `@axiomify/upload` handles
  what production apps need; supporting all of RFC 7578 §4.3 (custom
  charset declarations, etc) is yak-shaving.
